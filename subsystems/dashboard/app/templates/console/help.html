Running the service: tenants, their relays, and this server. Each tenant's own dashboard has its own Help page for its technicians.

1 Tenants

  • New tenant runs a job: checks the slug, creates the tenant, starts its relay on the next free port block, publishes https://<slug>.{{ provider_domain or "<provider domain>" }} with its own Let's Encrypt certificate, generates its client PDF guides, and invites its first admin.
  • The invite link is emailed and also shown in the job, valid for 3 days. Without provider email set up, send it yourself.
  • The tenant page shows usage (devices, technicians, session hours this month), the relay (ports, key, containers), the web domain and certificate, the plan, admins with their last sign-in, and the lifecycle actions.
  • Plan is free text for now, shown to the tenant on its home page.

2 Trial & subscription

  • New tenants start on a 14-day trial. Their dashboard shows the end date and days left on the home page and a banner on every other page.
  • Their admins are emailed 3 days before the end. When it ends the tenant is suspended automatically (checked hourly), and the admins are emailed again.
  • Activate — the tenant has subscribed: trial → active, and the trial notices go away.
  • Extend trial — adds days, counted from now if the trial has already ended.
  • Reactivate goes back to trial while trial time is left, otherwise to active. To give an expired trial more time, extend it first, then reactivate.

3 Suspend, cancel, purge

SuspendImmediate. The tenant's dashboard and download links show "not active"; its relay keeps running, so devices stay registered. For non-payment and the like.
Cancel (type the slug)Stops the relay (keys and data kept). The tenant's admins can only sign in to export CSVs. Purged after 30 days; admins are emailed at cancellation and 7 days before.
Extend grace periodPushes a cancelled tenant's purge date out.
ReactivateFrom suspended, or from cancelled within the grace period (the relay starts again with the same keys and ports, so devices reconnect on their own).
Purge now (type the slug)Deletes the relay, keys, files, domains and data for good. The slug and port block are never reused; usage history and the audit log are kept.

Tenant #1 can't be cancelled or purged.

4 Relays

  • Each tenant has its own relay (hbbs + hbbr containers) at <slug>.relay.{{ provider_domain or "<provider domain>" }}, with its own keypair and a block of 5 ports. Tenant #1 uses the default 21115–21119.
  • New tenants' ports come from {{ port_range }} (TCP and UDP), which must stay open in the cloud firewall.
  • Restart / Stop / Start / Upgrade per relay, or Upgrade all relays one at a time. A restart or upgrade briefly drops that tenant's active sessions.
  • Technicians' own RustDesk apps need their tenant's relay settings; each tenant's Help page lists them.

5 Jobs & audit log

  • Tenant creation, cancel, reactivate, purge and relay work run as jobs, one per tenant at a time, with each step and its result shown.
  • The audit log records every console action and scheduled event (trial warnings and expiries, purge warnings, provider emails). Tenants never see these entries.

6 Host health

  • Live CPU, memory (and swap), disk and uptime for this server, plus every tenant's relay containers.
  • Memory and disk show the alert threshold as a marker and turn amber within 10 points of it, red at it.
  • Set thresholds under Settings → Host health alerts. Every provider admin is emailed when usage stays above one (debounced), once per crossing.
  • Each tenant adds two relay containers, so memory is usually what limits how many tenants fit.

7 Backups

  • A backup covers every tenant relay's keypair (every client is tied to it) and peer registry, and the dashboard database. It runs nightly at 03:30 UTC; you can also back up on demand.
  • Set an off-site destination (Amazon S3, Wasabi, Backblaze B2, DigitalOcean Spaces, MinIO or another S3 endpoint), then Save & test connection and turn the off-site copy on. Local-only backups don't survive losing the server.
  • Set an encryption passphrase and keep a copy off this server: restoring needs it.
  • Retention is separate for each copy: local archives on the server (in /opt/rustdesk-fleet/backups), and off-site copies in the bucket (0 = keep all; pruning needs s3:DeleteObject).
  • Restore takes a safety snapshot first, replaces the keypairs and databases, and restarts the relays. With the same keys, clients reconnect without reconfiguration.
  • Off-site archives are listed too, with Restore (downloads, then restores; needs s3:GetObject) and Delete.

8 Code signing

  • Signs every tenant's Windows installers with Azure Trusted Signing (via jsign on this server), so clients don't see SmartScreen's “unknown publisher” warning. Setup steps: DEPLOYMENT.md → “Code signing”.
  • Fill in the Azure directory and application IDs, client secret, endpoint, account and certificate profile, then Save & test and turn signing on.
  • Sign automatically after each build (recommended), or tenants use Sign / Re-sign on their group pages.

9 Client version

  • Every tenant's installers are built with one pinned RustDesk client version. When a newer release is out, Update installers downloads it, optionally rebuilding every tenant's outdated installers in the background.
  • Installed devices keep their version until reinstalled (or updated by a group's automatic updates); download links always serve the newest build.

10 Settings & email

  • Provider email (SMTP) sends console invitations, host health alerts to every provider admin, and emails to tenants' admins: invites, trial warnings and expiry, cancellation and purge warnings. Send me a test email checks it.
  • Mail to tenants' admins goes to outside domains, so the mail server must allow relaying from this server, and the sending domain's SPF (and ideally DKIM) must cover it, or mail lands in spam.
  • Tenants set up their own SMTP for their own alerts, in their dashboard.
  • Let's Encrypt account email receives certificate notices for the tenants' and console's certificates.
  • The provider domain and relay port range come from dashboard.env and are shown read-only.

11 Provider admins

  • Provider admins sign in with passkeys only. Invite a provider admin emails a one-time enrollment link, valid for 1 hour; New enrollment link issues another for an existing admin.
  • Disable blocks an admin's sign-in at once; Enable restores it.
  • From the server shell: provider_admin.py --domain <provider domain> add | enroll-link … (DEPLOYMENT.md §11).
